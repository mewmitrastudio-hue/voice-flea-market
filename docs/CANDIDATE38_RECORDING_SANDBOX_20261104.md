## Original-device purchase records: stop, preserve, reconcile

Build37's native `koe-purchase-attempt.json` stores only product ID and order token. It cannot establish which backend owns an unresolved attempt. A Sandbox StoreKit environment alone does not establish database provenance.

Before creating any sandbox Supabase client, the app checks local durable action/purchase keys and the original native journal plus StoreKit unfinished transactions. Any legacy/foreign record, storage failure, malformed native response, unknown transaction ownership, or native-check failure blocks connection. A native v2 record proven to belong to this exact sandbox may connect for its owner’s recovery, but the preparatory purchase/recovery locks remain OFF. It does not clear, rename, expire, migrate, mark paid, or finish these records. Native purchase and finish remain blocked even if code tries to bypass the UI.

If blocked, do not uninstall, clear browser/app storage, delete records, finish transactions manually, or use a fresh order to hide the unresolved purchase. Resolve the exact original transaction/order through its original environment using a separately reviewed recovery path. Re-check on the same device after the original obligations are actually resolved. An empty StoreKit unfinished stream alone does not discharge a persisted Ask to Buy journal.

The gate deliberately also blocks unknown legacy checkout, voice, financial-evidence and message attempt keys. Even a seemingly stale key is not proof of cancellation. This may require review of old completed-attempt residue before this device can be used. No production connection or cleanup is attempted by candidate38.

## Separate Apple permission controls and permanent recording Stripe-write prohibition

The earlier “separate Apple enablement from Stripe writes” prerequisite is now implemented locally. All current values remain OFF:

- `RECORDING_APPLE_PURCHASES_ENABLED=false`: new voice/Boost purchases. This also requires recovery enabled before any future new purchase can start.
- `RECORDING_APPLE_RECOVERY_ENABLED=false`: receipt reconciliation, native finish and Apple delivery acceptance UI.
- `RECORDING_STRIPE_READS_ENABLED=false`: the existing status-only client read, independently controlled from Apple. Enabling Apple does not enable this read, and enabling the read cannot enable a write.
- `RECORDING_STRIPE_WRITES_ENABLED=false`: an invariant, not an enable switch. The recording client always returns false for Stripe-write permission, even if someone changes this value to true. Any missing/mistyped flag, incorrect environment or backend identity fails closed. The matching manifest fields are all false.

Native constants independently leave purchase and recovery/finish disabled and require Stripe writes to remain false. Startup checks native permission metadata against the exact client flags as well as the existing backend/environment/journal provenance. A stale binary, missing metadata or mismatch blocks connection. Hash/manifest verification enforces these current OFF values; no device or server-readiness result automatically switches them on. The current banner therefore continues to describe purchases and Stripe connection as stopped.

Native iOS checkout navigation reaches the Apple policy before the permanent Web checkout block. Web Checkout, Connect creation, renewal, cancellation and refunds remain blocked even with both Apple switches and Stripe reads hypothetically enabled. Apple acceptance remains available only after a future authorized recovery enable; its server-side channel is selected from the authenticated database payment, never from a client-supplied channel.
